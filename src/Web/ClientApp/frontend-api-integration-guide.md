## 2. Phase 0 — Understand the Backend Endpoint

Before writing any frontend code, gather three pieces of information from the backend:

### Step 0.1 — Find the Route

Open the endpoint file (e.g., [Products.cs](file:///d:/programming/CleanArchitectureNet10/CafePosBackend/src/Web/Endpoints/Products.cs)):

```csharp
public class Products : IEndpointGroup
{
    public static void Map(RouteGroupBuilder groupBuilder)
    {
        groupBuilder.MapPost(CreateProduct);       // POST /api/Products
        // groupBuilder.MapPut(UpdateProduct, "{id}");  // PUT  /api/Products/{id}
    }
}
```

The route is auto-generated by [WebApplicationExtensions.cs](file:///d:/programming/CleanArchitectureNet10/CafePosBackend/src/Web/Infrastructure/WebApplicationExtensions.cs):

```csharp
var routePrefix = $"/api/{groupName}";   // groupName = class name = "Products"
var group = app.MapGroup(routePrefix).WithTags(groupName);
```

So this endpoint is: **`POST /api/Products`**

### Step 0.2 — Find the Request Shape (Command)

The handler method signature tells you the command type:

```csharp
public static async Task<Created<Guid>> CreateProduct(
    ISender sender, 
    CreateProductCommand command)  // ← This is your request body
```

Open the command file ([CreateProduct.cs](file:///d:/programming/CleanArchitectureNet10/CafePosBackend/src/Application/Product/Commands/CreateProduct/CreateProduct.cs)):

```csharp
public record CreateProductCommand : IRequest<Guid>
{
    public string Name { get; set; } = string.Empty;
    public decimal Price { get; set; }
    public string ImageUrl { get; set; } = string.Empty;
    public bool IsAvailable { get; set; }
    public string? Description { get; set; }
    public Guid CategoryId { get; set; }
}
```

### Step 0.3 — Find the Response Shape

The return type `Task<Created<Guid>>` means:
- **HTTP Status**: `201 Created`
- **Response Body**: A `Guid` (the ID of the created resource)
- **Location Header**: `/Products/{id}`

> [!TIP]
> **Common return type patterns:**
> | Return Type | HTTP Status | Body |
> |---|---|---|
> | `Ok<T>` | 200 | The `T` object |
> | `Created<T>` | 201 | The `T` value |
> | `NoContent` | 204 | Empty |
> | `Results<Ok<T>, NotFound>` | 200 or 404 | `T` or problem details |

### Summary Table You Should Build

Before moving on, write down this table for your endpoint:

| Property | Value |
|---|---|
| **HTTP Method** | `POST` |
| **Route** | `/api/Products` |
| **Request Body** | `{ name, price, imageUrl, isAvailable, description?, categoryId }` |
| **Response Status** | `201 Created` |
| **Response Body** | `Guid` (string) |

## 3. Phase 1 — Ensure URL Resolution (One-Time Setup)

> [!IMPORTANT]
> This phase only needs to be done **once** per project. If you've already set this up, skip to Phase 2.

### How Aspire Injects the Backend URL

In [AppHost/Program.cs](file:///d:/programming/CleanArchitectureNet10/CafePosBackend/src/AppHost/Program.cs):

```csharp
var web = builder.AddProject<Projects.Web>(Services.WebApi)
    // ...

builder.AddJavaScriptApp(Services.WebFrontend, "./../Web/ClientApp")
    .WithReference(web)    // ← THIS injects the env var
    .WaitFor(web)
    // ...
```

`.WithReference(web)` makes Aspire inject an environment variable into the frontend process:
```
services__webapi__http__0=http://localhost:<dynamic-port>
```

### Step 1.1 — Update `vite.config.ts`

Vite only exposes env vars with specific prefixes to `import.meta.env`. By default, only `VITE_` is allowed. You must add `services__`:

```typescript
// vite.config.ts
export default defineConfig(({mode}) => {
  const env = loadEnv(mode, '.', '');
  return {
    plugins: [react(), tailwindcss()],
    // ▼ ADD THIS LINE ▼
    envPrefix: ['VITE_', 'services__'],
    // ...
  };
});
```

> [!WARNING]
> **Without `envPrefix`**, Aspire's injected `services__webapi__http__0` env var will NOT be available in `import.meta.env`. The URL resolver will silently fall back to `/api` (same-origin), which only works when the SPA is served by the backend itself.

### Step 1.2 — Update `api.ts` URL Resolution

The axios base URL must resolve from multiple sources (priority order):

```typescript
// src/Web/ClientApp/src/lib/api.ts

function resolveApiBaseUrl(): string {
  const env = (import.meta as any).env;

  // 1. Explicit override (e.g., set in .env or .env.development)
  if (env.VITE_API_URL) return env.VITE_API_URL;

  // 2. Aspire-injected service reference
  const aspireUrl = env.services__webapi__https__0 
                 || env.services__webapi__http__0;
  if (aspireUrl) return `${aspireUrl}/api`;

  // 3. Same-origin fallback (SPA served by the backend itself)
  return '/api';
}

const api = axios.create({
  baseURL: resolveApiBaseUrl(),
});
```

> [!NOTE]
> **Why append `/api`?** Aspire injects the raw origin (`http://localhost:5234`). Our Minimal API endpoints are mapped under `/api/{GroupName}` by `WebApplicationExtensions.cs`, so the axios base URL needs the `/api` prefix.

## 4. Phase 2 — Create a Typed API Service

For each domain entity or feature, create a dedicated service file in `src/Web/ClientApp/src/lib/`.

### Naming Convention

```
src/Web/ClientApp/src/lib/{entity}Service.ts
```

Examples: `productService.ts`, `categoryService.ts`, `orderService.ts`

### Step 2.1 — Define TypeScript Interfaces

Map each property from the backend command to a TypeScript interface. **Use the exact same property names as the C# command** (camelCase — ASP.NET Core's JSON serializer does this automatically):

```typescript
// src/Web/ClientApp/src/lib/productService.ts
import api from './api';

// Matches CreateProductCommand in C#
export interface CreateProductRequest {
  name: string;          // C#: string Name
  price: number;         // C#: decimal Price
  imageUrl: string;      // C#: string ImageUrl
  isAvailable: boolean;  // C#: bool IsAvailable
  description?: string;  // C#: string? Description  (nullable → optional)
  categoryId: string;    // C#: Guid CategoryId      (Guid → string)
}
```

> [!WARNING]
> **C# property casing:** ASP.NET Core's default `System.Text.Json` serializer converts PascalCase → camelCase automatically. So `CategoryId` in C# becomes `categoryId` in JSON. Always use **camelCase** in your TypeScript interfaces.

> [!WARNING]
> **C# `Guid` maps to TypeScript `string`**. Always send GUIDs as plain strings — ASP.NET Core deserializes them automatically.

### Step 2.2 — Write the API Function

```typescript
/**
 * POST /api/Products
 * Creates a new product and returns its ID (Guid).
 */
export async function createProduct(data: CreateProductRequest): Promise<string> {
  const response = await api.post<string>('/Products', data);
  return response.data;
}
```

**Pattern for other HTTP methods:**

```typescript
// GET /api/Products
export async function getProducts(): Promise<ProductDto[]> {
  const response = await api.get<ProductDto[]>('/Products');
  return response.data;
}

// PUT /api/Products/{id}
export async function updateProduct(id: string, data: UpdateProductRequest): Promise<void> {
  await api.put(`/Products/${id}`, data);
}

// DELETE /api/Products/{id}
export async function deleteProduct(id: string): Promise<void> {
  await api.delete(`/Products/${id}`);
}
```

> [!TIP]
> The path in `api.post('/Products', data)` is **relative to the baseURL** (`/api`), so the full URL becomes `/api/Products`. Don't include `/api` in the path again.

## 5. Phase 3 — Wire the Zustand Store

The store is the bridge between the API service and the UI. It manages state and orchestrates API calls.

### Step 3.1 — Import the Service Function

```typescript
// src/Web/ClientApp/src/store/useMenuStore.ts
import { createProduct } from '../lib/productService';
import toast from 'react-hot-toast';
```

### Step 3.2 — Add Loading State

Add an `isSubmitting` flag to prevent double-submissions:

```typescript
interface MenuState {
  items: MenuItem[];
  isSubmitting: boolean;                                    // ← ADD
  addItem: (item: Omit<MenuItem, 'id'>) => Promise<void>;  // ← Change to Promise
  // ...
}
```

### Step 3.3 — Implement the Async Action

Replace the mock implementation with a real API call:

```typescript
export const useMenuStore = create<MenuState>((set, get) => ({
  //                                          ^^^ need get() for the guard
  // ...
  isSubmitting: false,

  addItem: async (item) => {
    // Guard against double-submit
    if (get().isSubmitting) return;
    set({ isSubmitting: true });

    try {
      // ★ MAP frontend field names → backend field names ★
      const newId = await createProduct({
        name: item.name,
        price: item.price,
        imageUrl: item.image,        // frontend "image" → backend "imageUrl"
        isAvailable: item.isAvailable,
        description: item.description,
        categoryId: item.category,   // frontend "category" → backend "categoryId"
      });

      // Update local state with server-generated ID
      set((state) => ({
        items: [...state.items, { ...item, id: newId }],
      }));
    } catch (error: any) {
      const message = error?.response?.data?.title
        || error?.response?.data?.detail
        || error?.message
        || 'خطا در عملیات';
      toast.error(message);
      throw error;   // Re-throw so the UI can react (e.g., don't close modal)
    } finally {
      set({ isSubmitting: false });
    }
  },
}));
```

> [!IMPORTANT]
> **Field Mapping is Critical.** Your frontend model (`MenuItem`) and backend model (`CreateProductCommand`) may use different property names. Always map explicitly in the store action — never rename your frontend interfaces to match the backend, as that would couple them tightly.

> [!NOTE]
> **Why `(set, get)` instead of just `(set)`?** You need `get()` to read `isSubmitting` for the double-submit guard without causing a re-render.

## 6. Phase 4 — Update the UI Component

### Step 4.1 — Destructure the New State

```tsx
// src/Web/ClientApp/src/pages/AdminInventory.tsx
const { 
  items, addItem, updateItem, deleteItem,
  isSubmitting  // ← ADD
} = useMenuStore();
```

### Step 4.2 — Make the Submit Handler Async

```tsx
const handleSubmit = async (e: React.FormEvent) => {
  e.preventDefault();
  // ... validation ...

  try {
    if (editingItem) {
      updateItem(editingItem.id, payload);
      toast.success('محصول با موفقیت ویرایش شد');
    } else {
      await addItem(payload);   // ← AWAIT the async call
      toast.success('محصول جدید با موفقیت اضافه شد');
    }
    handleCloseModal();   // Only close on success
  } catch {
    // Error toast is already shown by the store
    // Modal stays open so user can fix and retry
  }
};
```

### Step 4.3 — Add Loading Feedback to the Submit Button

```tsx
<button 
  type="submit"
  disabled={isSubmitting}
  className={`... ${
    isSubmitting 
      ? 'bg-gray-400 cursor-not-allowed text-gray-200' 
      : 'bg-[#0f3229] hover:bg-[#0b261f] text-white'
  }`}
>
  {isSubmitting 
    ? 'در حال ارسال...' 
    : editingItem 
      ? 'ذخیره تغییرات' 
      : 'افزودن محصول'}
</button>
```

## 7. Checklist — Quick Reference

Use this checklist every time you connect a new endpoint:

```
□ Phase 0 — Understand the Backend
    □ Identify HTTP method + route from Endpoints/*.cs
    □ Read the Command/Query record for request shape
    □ Read the return type for response shape
    □ Note any field name differences vs. frontend models

□ Phase 1 — URL Resolution (one-time, already done ✓)
    □ envPrefix includes 'services__' in vite.config.ts
    □ api.ts resolveApiBaseUrl() handles VITE_API_URL + Aspire

□ Phase 2 — API Service Layer
    □ Create src/lib/{entity}Service.ts
    □ Define Request/Response TypeScript interfaces (camelCase, matching C#)
    □ Write async function using the shared axios instance
    □ Use correct relative path (e.g., '/Products' not '/api/Products')

□ Phase 3 — Zustand Store
    □ Import the service function
    □ Add isSubmitting (or isLoading) state
    □ Change action signature to return Promise<void>
    □ Use (set, get) in create() for the double-submit guard
    □ Map frontend fields → backend fields explicitly
    □ Handle errors with toast.error + re-throw
    □ Use finally {} to reset loading state

□ Phase 4 — UI Component
    □ Destructure isSubmitting from the store
    □ Make handleSubmit async, await the store action
    □ Wrap in try/catch (store shows error toast)
    □ Only close modal / reset form inside try (on success)
    □ Disable submit button during isSubmitting
    □ Show loading text on the button
```

## 8. Field Mapping Conventions

Your frontend and backend models will often differ. Here are the patterns in this project:

| Frontend (TypeScript) | Backend (C#) | Reason |
|---|---|---|
| `image` (URL string) | `imageUrl` | Backend is more explicit |
| `category` (ID string) | `categoryId` | Backend uses FK naming convention |
| `id` (string) | `Id` (Guid) | Guid serializes as a string |
| optional field `?` | nullable `?` | Direct mapping |
| `number` | `decimal` / `int` | JavaScript only has `number` |

> [!TIP]
> **Always map in the store, not the service.** The service should match the backend contract exactly (same field names). The store translates between the frontend model shape and the backend contract shape.

### Where Each Shape Lives

```
Frontend Model (MenuItem)          ← defined in useMenuStore.ts
         │
         │  field mapping happens here
         ▼
Backend Contract (CreateProductRequest)  ← defined in productService.ts
         │
         │  exact match (camelCase of C#)
         ▼
C# Command (CreateProductCommand)  ← defined in CreateProduct.cs
```

## 9. Error Handling Strategy

The project uses a three-layer error handling approach:

```
Layer 1: axios interceptor (api.ts)
  └─ Catches 401 → auto-logout + redirect to /admin/login
  └─ All other errors pass through

Layer 2: Store action (useMenuStore.ts)
  └─ Catches all errors → shows toast with error message
  └─ Re-throws the error so the UI can react

Layer 3: UI component (AdminInventory.tsx)
  └─ Catches re-thrown error → prevents modal close on failure
  └─ No duplicate toast (store already showed it)
```

### Reading Backend Error Responses

ASP.NET Core Minimal APIs return **Problem Details** on errors:

```json
// Validation error (400)
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "Name": ["'Name' must not be empty."]
  }
}

// Generic server error (500)
{
  "title": "Error summary",
  "detail": "Detailed explanation",
  "status": 500
}
```

That's why the store reads errors in this priority:
```typescript
const message = error?.response?.data?.title      // Problem Details title
  || error?.response?.data?.detail                // Problem Details detail
  || error?.message                               // Axios/network error
  || 'خطا در عملیات';                              // Fallback
```
